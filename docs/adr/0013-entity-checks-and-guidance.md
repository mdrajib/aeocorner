# ADR-0013: Entity checks and guidance: a profile is confirmed only if we could read it, "couldn't check" is never a failure, and we never write to other people's profiles

## Context

Engines name a business when they can tell it from a namesake. The evidence they use sits mostly on pages we do not own: a LinkedIn page, a Google Business Profile, a directory, Wikidata. Three things were hard to change once customers rely on them: what the Brand Kit holds about the entity (a one-way door, because every save is an immutable version), when a profile counts as "confirmed" (it ends up in a customer's structured data), and how far we go on other people's sites (we go nowhere).

## Decision

**1. The Brand Kit gains an `entity` section (schema version 2) and nothing stored is rewritten.** Founding year, where the business is based, profile links, and a Wikidata item number: every one of them stated by the customer, none filled in by us. The legal name stays in `identity`. A version-1 kit reads as a version-2 kit with the section empty, so `changedSections` does not report a change just because a kit predates the section. The platform of a profile is worked out from its address (`entity-profiles.js`), never asked for, so a customer cannot mislabel one. A Wikidata address pasted among the profiles becomes the item number.

**2. "We could not look" is `error`, never `failed`, and is never shown as a result.** One vocabulary for profiles and Wikidata (`entity_checks`, `status` passed / failed / error, plus a `finding` word). A profile is `failed` only if we read a page that does not name the business, or it answered 404 or 410. A firewall, a sign-in page, a page that builds itself in the browser, robots.txt shutting out our crawler, a server error, a timeout, an unreadable page, a lookup that was down: all `error`, which opens no recommendation, is not read as a failure by any screen, and keeps an issue already open from being cleared (its key stays "detected"). `robots.txt` is obeyed as `AEOCornerBot` for every profile, even for a customer whose own domain is verified: a profile is somebody else's website. The page is read by the same linear, depth-capped parser as every other page; it is never rendered in a browser (so LinkedIn will often be "couldn't check", and the screen says so).

**3. A real result outlives a later "couldn't check" for 30 days.** `entity_checks` holds the latest attempt. If the attempt could not look but the row already holds a `passed` or `failed` from the last 30 days, the row keeps it and records the failed attempt in `details.lastAttempt`; the screen says "we could not check again on…". Without this a profile confirmed last week would drop out of a site's structured data the day LinkedIn blocked us. Past 30 days the error replaces it.

**4. Only a confirmed profile goes into `sameAs`.** The home-page Organization fix for `readiness.D3` writes the profiles whose check **passed** (the page names the business), the founding year the customer typed, and the legal name, through the Milestone 11 machinery (one approval, a fingerprint of what was shown, undo). The links are not typed on its screen. A customer cannot make an unconfirmed link appear in their `sameAs` through this fix; the older logo and links form still exists for `readiness.C1` and writes what is typed, as before. **Open and deliberate:** a profile on a platform that always blocks us (LinkedIn, often) can never be confirmed, so it cannot be written by this fix. A person's own confirmation ("I looked, this is us") would close that and is not built: it would weaken "only checked profiles", and the customer can still add the link to their site themselves. Each Organization fix now keeps the logo, links and year an earlier fix wrote, because the plugin replaces the node as a whole. `foundingDate` accepts a year (`jsonld.js`).

**5. Wikidata is looked up with the public API, and an item is "yours" only if it points at your site.** `wbsearchentities`, `wbgetentities` and `wbgetclaims` for the official-website property (P856), checked against the API documentation on 2026-10-04; no key, no account; only the brand's own name and aliases (and the item number the customer typed) are sent. The host (`www.wikidata.org`) is a subprocessor entry. **Found** needs exactly one item whose official website is the customer's domain; one or more name matches without that is **ambiguous**; none is **no item**; a number the customer typed is **confirmed** by a name or website match and a **mismatch** otherwise. The rule says plainly when not to create an item: Wikidata keeps an item only if it has a Wikipedia article, is needed by another item, or has identifiers and serious public sources (checked 2026-10-04 against secondary sources), so a new or local business may not qualify, and the recommendation has a low prior and a high effort for that reason. We never write to Wikidata or to Google's Knowledge Graph.

**6. Entity accuracy compares three facts, and leans away from accusing an engine.** From the brand's `claims` in answers to the active brand-intent questions, in the last 28 days: the founding year, where it is based, and price amounts (against the dollar amounts in the offerings). A fact is compared only if the customer stated it. A claim with two amounts is right if either matches; a place is right if it shares a word with the customer's; a claim we cannot read is not counted. "Not mentioned" is neutral, and with no brand answer read at all it is `unknown`, never "not mentioned". `entity.wrong_fact` needs at least two wrong statements in the window (one answer can be noise).

**7. Guidance for what we cannot touch is text for the customer to use.** Checklists for Google Business Profile, LinkedIn, Crunchbase, Wikidata and a trade directory (`entity-guidance.js`): steps, and every field filled only from the Brand Kit; what is missing is listed with where to add it. We create no account and post nothing. Limits (Google description 750 characters with no links, prices or promotions; LinkedIn tagline 120 and About 200 to 2,000) were checked on 2026-10-04 against secondary sources, and each checklist says to follow the platform's own screen where it differs.

**8. Rules are judged one by one.** `entity.wrong_fact:<fact>`, `entity.profile:<platform>-<hash of the address>` (a key column is 191 characters), `entity.wikidata:item`. `reconcile` now looks for a rule's own code in `evaluated` before its family, so a week of readable answers never clears a profile issue. None has an automatic re-check (the profile is looked at again by the next check, and "Check now" on the Entity screen does it at once); the lifecycle already sends such fixes straight to measuring.

**9. The About page uses the Content Studio as it is.** `readiness.D2` produces an `about_page` format (a new value at the end of the `content_items.format` enum) through the usual research, plan, draft, check and person's approval. Its headings are the questions a stranger asks (who, what, for whom, where, since when, why trust it). The year and the place are added to the facts a draft may state only if the customer typed them, at the end of the Brand Kit facts so no existing numbering moves. `BRIEF_VERSION` is `b2`. It is marked up as an Article; an `AboutPage` type is a possible later change. It has not run against the live model.

## Consequences

- A weekly sweep (`entity.sweep`, 03:50 UTC) and every Brand Kit save of the entity section queue `entity.check`. Nothing in it costs money, so it does not go through `callProvider`.
- The checks and the accuracy comparison are deterministic and tested over fixtures; hostile-input tests cover the profile reader (deep nesting, a megabyte word, thousands of links) and the claim reader.
- A confirmed profile that is later edited to remove the business's name becomes `failed` at the next real check, and the next `sameAs` fix would no longer include it; a `sameAs` already on the site stays until the customer undoes the fix or applies a new one.
- Not decided here: a person's confirmation of a profile we cannot read, a browser-rendered read of LinkedIn, an `AboutPage` type, and writing anything to another site.

## Addendum 2026-10-06: a person can confirm a profile we are not allowed to read

**Problem.** Some platforms never let our crawler read a profile. LinkedIn's robots.txt allows only its own bot and a short list of approved search engines, so a LinkedIn check ends as "couldn't check" for ever, and the profile can never reach `sameAs`. Other apps get around this by ignoring robots.txt, using a signed-in session or buying data; we obey robots.txt on profile pages (decision above) and will not do any of those.

**Decision.** A person with edit rights can say they opened the profile themselves and it describes the business.
- It is the customer's statement, stored in its own columns (`confirmed_at`, `confirmed_by_user_id`) and shown as "Confirmed by you". The check's `status` stays what the crawler found; a confirmation is never a `passed`.
- Allowed only while the latest check is `error`. A page we could read and found wanting (`failed`) is fixed on the page, not confirmed away; a `passed` one needs nothing.
- Any later real result (`passed` or `failed`) clears it: what we read outranks what a person said. A "couldn't check" keeps it. Changing the profile address starts clean, because the confirmation belongs to the address.
- A confirmed profile may go into the `sameAs` of the Organization fix (`readiness.D3`). The customer still sees the exact code and approves it before anything is written, so the statement is theirs and reviewed.
- Written to the activity log (`entity.profile_confirmed`, `entity.profile_unconfirmed`). No foreign key on `confirmed_by_user_id`: it is an audit trail and must outlive a user.

**Cost of being wrong.** A person could confirm a profile that does not name the business. The effect is one extra link in a structured-data block they reviewed, which they can take back at any time. A wrong claim never reaches the numbers: confirmations are not read by any score or recommendation rule.
