## Context

Milestone 8 puts money, other people's analytics logins, email to real inboxes and powerful staff screens into the product. Five things are hard to change once customers exist: who decides what a customer has paid for, what happens when Stripe and we disagree, how a Google login is held, what stops us emailing someone who asked us to stop, and what makes a staff action trustworthy.

## Decision

**1. Stripe is the source of truth for money; we keep a copy and re-ask.** Checkout and the Customer Portal are Stripe's own pages: a card number never touches us. Every webhook (checked by signature on the raw body, recorded by event ID in `webhook_events`, a repeat answered "duplicate") is applied by **asking Stripe for the subscription as it is now** and writing that, instead of trusting the order events arrive in (Stripe's own advice, checked 2026-10-04). So a replayed, late or out-of-order event cannot change anything: the same Stripe object always writes the same rows. A daily reconcile asks about every live subscription and says so (an alert) when the copy was behind. The organization's plan and status follow its *current* subscription (the latest one still paying), so a late event about an old cancelled subscription cannot overwrite a new one.

**2. Plans are enforced exactly when there is a way to pay.** With `STRIPE_SECRET_KEY` set (`config.billingEnforced`), an organization with no subscription can set a project up but nothing that costs money runs (tracking, "check now", drafts, publishing, the weekly scheduler), and a lapsed or cancelled one is paused or read-only. Without a key (a laptop, every test that is not about billing) nothing is locked. The rules are pure (`src/core/entitlements.js`): a limit of `NULL` is "not enforced", never zero; a grant adds to a number but cannot create one; the access levels are `full`, `grace` (seven days after a failed payment), `setup`, `paused`, `readonly` (cancelled, 90 days) and `ended`. Questions are counted across the organization's projects, as the plan table's numbers are (50 / 150 / 500 for 1 / 3 / 10 projects).

**3. The decisions that were proposals are now built, with these numbers:** a 14-day card trial once per organization (a returning customer pays from day one); a 30-day money-back window opened by the first real payment (D9); a seven-day grace period after a failed payment, started once; 90 days read-only after cancellation, a warning email 14 days before, then the organization is closed (`deleted_at`, `purge_after` +30 days). **The purge itself, the deletion of the rows, is not built** (MILESTONES task 8.24 builds the clock and the closing; the deleting job comes with the data-request work). Add-on prices are a hypothesis like the plans: extra questions at $19 a pack of 25, extra drafts at $5 each (a metered Stripe price; each draft past the allowance is one meter event with an identifier that names the organization, month and running total, so asking twice is a duplicate Stripe refuses).

**4. Only the worker opens a secret.** The Google refresh token is envelope-encrypted by the web process in the sign-in callback ([ADR-0011](0011-content-studio-and-wordpress.md) decision 5: the web process only encrypts) and opened by the sync job. To show the property picker without opening it again, the properties and sites the login can see are listed once, while the short-lived access token from the sign-in is still in memory, and stored as plain choices. Two read-only scopes, nothing else; the sign-in's `state` is signed together with a value tied to the signed-in session and expires in ten minutes, so someone else's sign-in cannot be finished in your browser.

**5. Email: dedupe, suppression, one proactive message a day, and a link that works.** Every email goes through one notifier (`src/lib/notify.js`): a row per message under a dedupe key (so a retried job sends once), the suppression list checked first (bounces and spam complaints arrive from Resend's signed webhook; a temporary bounce does not suppress), at most one proactive message (digest, alert) per person per day, and an unsubscribe link in every proactive message that works with no sign-in (RFC 8058 one-click `List-Unsubscribe` headers; opening the link changes nothing, pressing the button does). Messages about the account itself (a trial ending, a retention warning, a Google login that stopped) are not optional. The digest is built from the dashboard's own figures and keeps its rules: a figure that could not be read is "Couldn't check", a change is coloured only if it passed the significance test. Alerts are for significant drops, a significantly rising competitor and negative claims; each is told once.

**6. The staff console has one wall and an audit that comes first.** Every module is behind the same four checks (Cloudflare Access, a staff Clerk session with a second factor, an active staff row, the module's role), set once for all module paths; a test lists every route and fails if one is added without being checked. Every change goes through `audited()`, which writes `admin_audit_log` **before** the change and refuses the change if it cannot write. A reviewer sees an answer and the names being tracked, never the customer. Feature flags are switches the code reads (`digest.weekly`, `alerts.emails`, `google.sync`), on unless a person turns them off, with a per-organization override; a flag nobody created is off, except the ones the application itself reads.

## Consequences

- A customer who pays through Stripe is on the right plan within seconds of the webhook, and within a day even if the webhook is lost. A Stripe outage makes the webhook answer 500 and Stripe sends it again.
- Nothing about billing has run against Stripe: the tests use a stand-in on a real socket. The first live check is `npm run stripe:sync` against a test-mode key, then a test card (MILESTONES 8, Definition of Done). The same is true of Google: fixtures are built from Google's documentation, and Google's OAuth verification (task 0.18) takes weeks.
- The plan limits that are still `NULL` (task 0.17: seats, "check now" runs) behave as before: placeholders of 4 for drafts and "check now", no limit on seats.
- A cancelled account is closed but not yet purged: the data is hidden, not gone.
- Disconnecting Google erases our copy of the login but cannot tell Google (the web process cannot open the token); the screen says how to remove the app in the person's Google account.
- Alerts need a plan with the `alerts` feature (Growth and Agency); the digest is for everyone.
