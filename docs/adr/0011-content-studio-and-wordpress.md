# ADR-0011: Content Studio and WordPress: nothing goes live without a person, nothing is trusted from a model, and the connection is signed

## Context

The Content Studio writes pages for a customer's business and, through WordPress, puts them on the customer's site. Four things are hard to change once customers have pages and credentials in the system: what a model is allowed to claim in a page, who can make something go live, how we hold a customer's WordPress password, and how we know the test environment is real.

## Decision

**1. A model writes words; code decides facts.** Every step that calls Claude has its output checked in code, never trusted ([the pattern of ADR-0010](0010-recommendations-and-proof.md)):

| Step | What the model does | What code checks |
|---|---|---|
| Research (7.04) | Searches and reads the web (Anthropic's server-side `web_search_20250305` and `web_fetch_20250910`, checked against the docs on 2026-10-04; $10 per 1,000 searches, fetching costs only tokens) and lists facts with an address and a quotation | A fact is kept only if its address is one the tools actually returned, and a quotation is found in the page text the fetch returned or the passage the search cited. A quotation a fetched page does not contain drops the fact. A fact whose quotation could not be checked is shown to the customer as unchecked and **never given to the draft** |
| Plan (7.05) | Format, an outline of question headings with a direct answer of 60 words or fewer, entities, links, schema type | Every heading is a question, every answer is at most 60 words, every fact id exists, every internal link is one we offered (a made-up link is dropped, not trusted). The customer's edit of the plan goes through the same rules |
| Draft (7.06) | Writes the page as HTML, streamed | Sanitized to a short list of tags (`src/core/content-html.js`); a link to anything but a researched source or the customer's own site is unwrapped; a reply cut off at the token limit is never saved |
| Structured data (7.01) | Nothing: JSON-LD is built from the page by typed templates (`content-schema.js`) | Validated against a schema.org vocabulary (`jsonld.js`) before every save and again before it is sent; text that could end a `<script>` block is refused |
| Quality check (7.07) | Nothing: seven checks in code (`content-qc.js`): answer-first, claims have sources, headings, reading level, words to avoid, overlap with the site's own pages, structured data. Weights are v0 guesses | A `[needs source]` marker, an invented quotation, a near copy of an existing page or invalid structured data **blocks approval**; a low score alone does not |

**2. Approval is a person, and it pins one revision.** The lifecycle is one table (`content-lifecycle.js`): the system moves an item through research, plan, write and check to `ready`; only a person moves it to `approved` or starts publishing; only the system finishes publishing. Approving pins the exact revision (`approved_revision_id`, with a database CHECK that `approved`, `publishing` and `published` need an approval), and any edit takes the approval away. A test walks the table to prove no path reaches `published` without a person. A draft costs a month's allowance when it starts (a refresh counts half) and is given back if it fails before a draft exists; `DRAFTS_PLACEHOLDER` (4) applies until the founder sets plan limits (task 0.17).

**3. The WordPress test instance (7.02): three layers.**

| Layer | What it is | Runs |
|---|---|---|
| Stand-in | `tests/helpers/wordpress-stub.js`: speaks the REST calls we use and the plugin's routes, with the same signature rule | Every test run (no network, no PHP) |
| Real WordPress | `tests/wordpress/contract.test.js`: **WordPress Playground** (WordPress and PHP compiled to WebAssembly, run by Node) with this repository's plugin mounted and activated; the app's own client drives it | `npm run test:wordpress`, on demand and before a release; first run downloads WordPress. Playground is fetched with `npx` at a pinned version, not added to `package.json` (it is half a gigabyte) |
| A real site | The founder's staging WordPress | Before launch (Milestone 10); not automated |

Why not Docker or a hosted instance: no Docker on this project, and a hosted instance is a shared mutable thing every test run would fight over. Playground is disposable and local. The contract test also proves the plugin's claims: it was run on **WordPress 6.2 with PHP 7.4** (the plugin's stated minimums) and on the latest WordPress (7.1.2) with PHP 8.5; `WP_PHP=7.4 WP_WP=6.2 npm run test:wordpress`. Note: Playground's `--php` and `--wp` command-line flags are **ignored when a blueprint is given**; the versions are set in the blueprint (`preferredVersions`), and the test asserts the versions the plugin itself reports, because an earlier run that only passed the flags was silently running PHP 8.5.

**4. The connection is signed, and writes go through the safe fetcher.** Everything we send to a customer's site goes through `createSafeFetcher` ([ADR-0005](0005-fetching-other-peoples-websites.md)); it gained `POST/PUT/PATCH/DELETE` with a body. A request that carries a credential (`authorization`, `cookie`, `x-aeo-*`) or changes something is **never redirected**, so a credential cannot follow a redirect to another host. Two layers talk to WordPress: its REST API with an application password (create and update posts), and the plugin's routes (`/wp-json/aeocorner/v1`), each signed with a per-site secret: `HMAC-SHA256` over `AEO1`, timestamp, nonce, method, **route** (not address, so sub-folder and plain-permalink sites sign the same thing) and the body's SHA-256; five-minute window, each nonce once. The JavaScript and PHP implementations are separate and the contract test runs them against each other, including wrong secret, old clock, replay and a signature for another route or body.

**5. Credentials are envelope-encrypted and the web process only encrypts.** `src/lib/secrets.js`: each secret has its own AES-256-GCM data key, wrapped with a master key from the environment (`SECRETS_MASTER_KEY`, never in the database or repository), both bound to a context (`wordpress:<org>:<project>`) so a ciphertext copied to another row does not open; rotating the master key re-wraps 60-byte data keys. The connect screen encrypts what the person typed; only the worker opens it (publishing, the connection check, and the plugin handshake it runs when a plugin is installed later). A password is never put back in a page or a log, and a typed one is not echoed on an error.

**6. The plugin does one thing and can be left with one click.** `wordpress-plugin/aeo-corner-connector/` (PHP 7.4+, WordPress.org rules): prints the approved JSON-LD in `wp_head` on the server (most AI crawlers do not run JavaScript), sets a page's title and description (Yoast and Rank Math filters), serves the IndexNow key and pings IndexNow when asked. JSON is encoded once, when saved, with `<`, `>` and `&` as escapes. It accepts only addresses of its own site and has a Settings → AEO Corner page with Disconnect, which erases everything. Without the plugin the structured data travels inside the post, where WordPress may strip it for some users; the live-page check after publishing says so.

**7. Publish → done → baseline, then the page is looked at.** Publishing records a `site_changes` row (what, to which connection, who approved), remembers the WordPress post id **before anything else can fail** (a retry updates, never duplicates), and ends `published` (live) or leaves the item `approved` when only a WordPress draft was made. When a page goes **live**, the recommendation behind it is started and marked done by the person who approved (`markDone` saves the 28-day baseline), and its re-check is **`url_live`**: the page is fetched as a crawler would and must exist, not be `noindex`, show its headline and carry the structured data we sent, at once, +1 hour and +24 hours (`src/core/live-check.js`). As with readiness fixes, "we could not look" is never "your fix failed". This is the live-URL check [ADR-0010](0010-recommendations-and-proof.md) promised.

**A refresh replaces a page in place.** A refresh item's address is resolved by the plugin (`/resolve`) every time it publishes (a retry must know whether the address is a post or a page; the REST routes differ), and the post or page is updated through its own route; only posts and pages are supported. WordPress cannot hold an unpublished version of a published page, so "save as a WordPress draft" is refused for a refresh (it would take the page down). Without the plugin, or when the address is not found, nothing is changed and the customer is told why. A publish that fails marks its `site_changes` row failed, so no change is left "working".

**8. The editor is TipTap, bundled and self-hosted, with its CSS injection off (7.08).** `npm run build:editor` bundles TipTap 3 (`@tiptap/core`, starter kit, table) with esbuild into `src/web/public/vendor/editor.js` (423 KB, committed like the other vendored assets, loaded only on the item page). The CSP is unchanged. What was checked: TipTap's `injectCSS` creates a `<style>` element, which `style-src 'self'` forbids, so it is switched off and the editor's look is in `tailwind/components.css`; ProseMirror's own style changes are CSSOM assignments, which the CSP allows. The Playwright flow loads the editor, types, saves, and fails on any console error, which includes CSP violations. The page works without JavaScript: the draft is a plain textarea of HTML that the editor upgrades; the server sanitizes whatever is posted.

### Addendum 2026-10-04: auto-fix approval (UI_DESIGN D3)

The plugin can write one thing besides a post: a JSON-LD block for an address. So auto-fix is offered only for the two readiness checks that block fixes (C1 Organization, C4 WebSite) on the home page. It reuses the publish pattern: a person approves exactly what they previewed (a fingerprint of the data travels with the approval), a `site_changes` row records it, a job writes it, and the recommendation is marked done with the same-day re-check. Robots.txt, sitemap and title fixes (A1, A4, F3) are still guidance: the plugin has no way to change them, and the rules table keeps its `auto_fix` label for them until it does. The plugin replaces the block for an address, so each fix writes the whole graph. **Undo (2026-10-04):** the same screen takes a written fix off the site. The plugin keeps one block per address, so undoing means putting back what was there before the change (`site_changes.previous_value`) or deleting the block if nothing was; therefore only the latest applied change for an address can be undone. A person's request claims the change (`rolled_back_by_user_id`), the worker does the removal through the plugin, and only a removal that really happened marks it `rolled_back` and steps the recommendation back to in progress, clearing its baseline, re-checks and measurement (the fix they described is gone). A failed removal releases the claim with a plain reason and changes nothing else. The system-only move back to `in_progress` is the only way the lifecycle table lets a done or measuring fix be reset.

## Consequences

- A page can be wrong about nothing the facts registry does not support, and the customer can see which facts were checked. The cost is blandness: a topic with no checkable facts gets a draft built from the Brand Kit alone, and the screen says so.
- The model-written research, plan and draft have **not run against the live model yet**; their prompts and the checks above are tested with stand-ins. The first live run is the first check of quality and cost (estimated at about $0.30–0.40 a draft on Opus 5.5 with six searches).
- Hosting Playground-style tests means the first `npm run test:wordpress` downloads about 25 MB of WordPress and takes two to three minutes; it is not part of `test:all`.
- The contractor option for the plugin (task 7.11) was not needed: the plugin is small enough to be written and verified here. A WordPress.org submission (their review, assets, a readme) is a separate step, not done.
- Google OAuth for GA4 reuses the same `integrations` table and `secrets.js` in Milestone 8.
